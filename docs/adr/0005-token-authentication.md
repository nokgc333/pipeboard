# ADR-0005: トークン認証とロールを導入する（ADR-0004 を置き換える）

## Status
Accepted (2026-10-25). Supersedes [ADR-0004](0004-no-auth.md).

## Context
v1 は個人開発のデモとして認証なしで作ったが、実運用に近づけるには、未認証のリクエストを拒否し、
権限のない操作を止める必要がある。一方で、ローカルでの開発・デモは、これまでどおり設定なしで動かしたい。

## Decision
- `PIPEBOARD_AUTH_MODE` で 2 つのモードを切り替える。
  - `local`（既定）: 認証なし。すべてのリクエストを管理者として扱う。自分のマシン内の利用を前提とする。
  - `token`: `Authorization: Bearer <token>` を必須にする。未認証は 401、権限不足は 403。
- トークンは `PIPEBOARD_API_TOKENS="viewer=...,editor=...,admin=..."` で環境変数に渡す（12 文字以上、役割をまたいだ重複は不可）。
  比較は `hmac.compare_digest`（一定時間比較）。起動時に設定を検証し、誤りがあれば起動を失敗させる。
- ロールは 3 段階。viewer は閲覧、editor は作成・更新・ステータス変更・コメント・アップロード、admin は削除を含む全操作。
  権限の判定は、リソースの存在確認より前に行う（存在の有無を権限のない相手に漏らさない）。
- CORS の既定は `http://localhost:3000` のみ。`*` は `PIPEBOARD_CORS_ORIGINS=*` と明示した場合だけ。Cookie は使わず、`allow_credentials` は常に無効。
- レート制限は、クライアント IP ごとの固定窓（60 秒）。読み取りと書き込みで別枠（既定 300 / 60 回）。`/healthz` は対象外。
- アップロードは、拡張子・Content-Type に加えて、先頭バイト（マジックナンバー）を検証する。

## Consequences
良い: 外部公開時に、トークンの発行だけで閲覧専用・編集可・管理の使い分けができる。ローカル利用の手間は変わらない。
      トークンは Cookie ではなくヘッダで送るため、CSRF の対象にならない。
悪い: トークンは環境変数で静的に管理する（失効・ローテーションは再起動が必要）。ユーザー個人の識別（監査ログ）はできない。
      フロントエンドがブラウザからトークン付きで API を呼ぶ場合、`NEXT_PUBLIC_API_TOKEN` は配信されるJSに含まれる。
      そのため、この組み合わせは信頼できるネットワーク内か、閲覧専用トークンに限る。公開サイトでの編集には、
      ログイン画面とセッション管理（OAuth2/OIDC など）が別途必要になる。
      レート制限はプロセス内のメモリ上で数えるため、複数プロセスや複数台では合算されない。

## Alternatives Considered
- OAuth2/JWT: 個人を識別できるが、IdP・ログイン画面・セッション管理が必要で、現段階では過剰。
- Cookie セッション: ブラウザには自然だが、CSRF 対策が必須になる。ヘッダのトークンなら不要。
